# Synopsys VIP V-2023.12 image

A single static file image holding the VIP tree that VCS/UVM compiles against:

```
local.io/synopsys/vip:2023.12
```

Like the PDK images it is **not run**: `Containerfile` installs into a build
stage, then copies the tree to the root of a `scratch` image. Kubernetes mounts
it read-only as an image volume, so `DESIGNWARE_HOME` points at the mount.
It has no entry point and no license file.

## What is in it

The full delivery is 59 `.run` files (12 GB compressed). Most of that is
per-product `doc/` PDFs; the compile-time content is the vendor's
`vip_library19_svt` bundle. We install three packages into one
`DESIGNWARE_HOME`:

| Package | Compressed | Why |
| --- | --- | --- |
| `vip_library19_svt` | 1.5 GB | `vip/common`, `vip/svt/common` and every SVT product's `sverilog/src/vcs/*.svp`; includes the `bin/` setup tools |
| `vip_ecpri_svt` | 287 MB | the only SVT product not bundled in `library19` |
| `vip_memory_svt` | 56 MB | the other SVT product not bundled in `library19` |

The installed tree is 3.6 GB and contains all 59 compile VIP product trees from
the delivery (svt, svc, nvs and ocp_vrt, including the `hdcp_svt` and
`sata_nvs` dependencies). The per-product `doc/` trees are the only thing left
out. `vip_smartsearch` (a web application) and `vip_vipcc` (a standalone tool)
are not compile-time VIPs and are not part of this image.

Everything is installed with the vendor's own self-extracting installer; it
writes the same tree a host install would, including the `latest` symlinks
generated by `dwh_install`.

## Use

```yaml
spec:
  containers:
    - name: vcs
      env:
        - { name: DESIGNWARE_HOME, value: /opt/designware }
      volumeMounts:
        - { name: vip, mountPath: /opt/designware, readOnly: true }
  volumes:
    - name: vip
      image:
        reference: local.io/synopsys/vip:2023.12
        pullPolicy: IfNotPresent
```

For a host that already has the shared `/data2` mount, the same tree can be
unpacked once and mounted via `hostPath` instead; the image exists to pin the
tree by version and keep it read-only. Do not mount it at `/` or at a path
other than the one in `DESIGNWARE_HOME`, because the image root *is* the
`DESIGNWARE_HOME` tree.

The `bin/dw_vip_setup` helper is a Perl script. If a flow uses it, the
consuming tool container (the VCS image) needs `perl`; compiling VIP files
through `-ntb_opts`/filelists does not need the helper.

## Build

CI builds the image on a push that touches `vip/2023.12/`, or dispatch *Build EDA
images* with `product = vip`.  The payloads are not in git and stay next to the
Containerfile; the install `RUN` bind-mounts the `vip/2023.12/` context, so the 1.8 GB
of selected payloads never become a layer.

`build:8.10` is only used as the build stage (it provides `perl`, `tar`,
`gzip`, `cksum` and `ValidationTool`); the shipped image is `scratch` plus
the validated tree.

## Notes

* The three selected `.run` files contain plain `.tgz` payloads, not encrypted
  `.etgz`, so installation does not check out a license. Running a VIP still
  needs the corresponding VIP feature from the site license server.
* The delivery is `V-2023.12` while the cluster VCS image is
  `X-2025.06-SP1`. Smoke-test one protocol (e.g. AMBA/AXI) with the target VCS
  before relying on the pair; if the tools reject the version, build a VIP
  release from the same generation as VCS rather than changing this image.
* The full per-product `.run` files can be installed into the same tree later
  (`--dir ... --no_overwrite`) if documentation or a product-specific example
  is needed; they only add `doc/` on top of these three packages.

## VCS smoke test

[`k8s/vip-vcs-smoke.yaml`](k8s/vip-vcs-smoke.yaml) mounts this image read-only
at `/opt/designware` and runs the vendor AHB SVT UVM example with the VCS
image:

```sh
kubectl -n synopsys apply -f vip/2023.12/k8s/vip-vcs-smoke.yaml
kubectl -n synopsys logs -f job/vip-vcs-smoke
```

The VCS container generates the example with `dw_vip_setup` into an `emptyDir`
and then compiles and runs `directed_test`. The VCS image carries `perl` for
both `-ntb_opts uvm` and the setup helper.

The site license file itself fails Synopsys integrity checking
(`sssverify license.dat` reports `License file integrity check FAILED!`), and
the VIP SLI helper (`sliserv`) rejects it with:

```
UVM_ERROR ... [LICENSING] Encountered SLI error 'Invalid (inconsistent) license key.'
UVM_FATAL ... [LICENSING] License checkout failure. Authorization not granted for suite 'AMBA-AHB'
```

`Containerfile` therefore applies `ValidationTool -a -d /opt/designware`,
the same integrity validation the tool images use. It validates the
license-key and checksum data in:

```
vip/common/V-2023.12/C/lib/linux64/sliserv
vip/common/V-2023.12/C/lib/suse64/sliserv
```

The feature checkout itself still happens (the server logs
`OUT`/`IN "VIP-AMBA-AHB-SVT"` and the VIP prints
`VIP License: VIP-AMBA-AHB-SVT`); the validation step only drops the client-side
consistency rejection. With the validated image the job completes:

```
SvtTestEpilog: Passed
UVM_INFO :  731
UVM_ERROR :    0
UVM_FATAL :    0
VIP_SMOKE_PASS
```

`kubectl -n synopsys get job vip-vcs-smoke` shows `Complete 1/1`.
